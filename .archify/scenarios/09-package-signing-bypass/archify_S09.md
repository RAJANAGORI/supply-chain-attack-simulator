## Verdict in one line

Package signing bypass spreads damage because signature verification passes when the attacker uses a stolen legitimate signing key, and behavioral analysis is the only way to detect the compromise.

---

## Why this lab exists

Real campaigns (SolarWinds, npm package maintainer key compromises) show attackers stealing code signing certificates and using them to sign malicious packages. Victim verifies the signature and sees VALID, trusts the package, and installs it. Signature verification alone cannot detect this attack. Scenario 09 copies that chain on localhost:

| Real campaign claim | Lab stand-in |
|---|---|
| Attacker steals signing key | Ed25519 keypair generated and used for both packages |
| Malicious package signed with stolen key | compromised secure-utils v1.0.1 signed |
| Signature verification passes | verify-signature.js shows VALID |
| Postinstall runs | compromised secure-utils postinstall.js fires |
| Secrets sent to attacker | `POST http://127.0.0.1:3000/collect` |

Safety never leaves the box: `TESTBENCH_MODE === 'enabled'` gates the malicious path, and every beacon stays on `127.0.0.1`.

## System map (what the architecture diagram encodes)

### Actors and runtime units

1. **Control Center** (`apps/control-plane`, UI `:3100`, API `:3101`)  
   Registers scenario 09 with port `3000`, one service, install/run steps, and one capture URL.

2. **setup.sh**  
   Sources `scenarios/_shared/enable-testbench.sh`, creates mock-server.js, generates Ed25519 keypair, signs both legitimate and compromised secure-utils packages with the same key.

3. **Ed25519 keypair (signing-key.pem)**  
   Generated by infrastructure/keygen.js. Used to sign both packages. In a real attack, the attacker steals this key.

4. **sign-package.js**  
   Signs a package directory with the Ed25519 key. Creates `.signature` file in package root.

5. **verify-signature.js**  
   Verifies package signature using the public key. Returns VALID for both legitimate and compromised packages because they are signed with the same key.

6. **legitimate secure-utils (v1.0.0)**  
   Clean package signed with the legitimate key.

7. **compromised secure-utils (v1.0.1)**  
   Malicious package signed with the stolen key. Postinstall.js exfiltrates system info to `:3000/collect` when TESTBENCH_MODE is enabled.

8. **victim-app**  
   Installs compromised secure-utils v1.0.1. `npm start` still works after compromise.

9. **Mock C2 server**  
   - `mock-server.js` → `captured-data.json`  
   - Validates POST /collect payload and logs captures  
   - Optional Elasticsearch forwarding via `SCAS_ES_URL`

10. **signature-validator.js**  
    Detection tool that performs behavioral scan of installed packages, beyond just signature verification.

### Trust boundaries on the diagram

- Region **127.0.0.1 lab only** wraps all components (keypair, signers, packages, victim, mock C2, capture file).  
- Security group **TESTBENCH_MODE=enabled** wraps only the compromised-pkg node. Outside that gate, postinstall returns immediately.

## Attack chain (what the sequence diagram encodes)

### Chain 1 - Setup (Control Center step 1)

`./setup.sh` creates mock server, generates Ed25519 keypair with infrastructure/keygen.js, signs legitimate v1.0.0 and compromised v1.0.1 packages with the same key.

### Chain 2 - Start listener (step 2)

Mock C2 must show Running on `:3000`. If down, exfil fails quietly and Inspector stays empty.

### Chain 3 - Verify signature (before install)

```bash
node infrastructure/verify-signature.js compromised-package/secure-utils
# Output: ✅ VALID (key matches)
```

Signature verification passes because the key fingerprint matches. This gives false confidence.

### Chain 4 - Install (the attack)

```bash
cd victim-app
export TESTBENCH_MODE=enabled
npm install ../compromised-package/secure-utils
```

npm runs compromised secure-utils postinstall before the app starts. Signature was valid, so victim trusts the package.

#### Phase A - npm installs signed package

1. npm installs compromised secure-utils v1.0.1.  
2. Package has valid signature (signed with stolen key).  
3. npm runs postinstall.js.

#### Phase B - Postinstall exfil

1. Postinstall.js runs when npm install completes.  
2. Reads hostname, username, platform from environment.  
3. `POST` to `:3000/collect` with payload marked `signatureStatus: valid` and `keyCompromised: true`.

#### Phase C - Cover story

`npm start` still works. Victim sees secure-utils functions working. No runtime errors. Damage is in captured-data.json.

## Blue team / containment talk track

Hunt the correlated shape, not just signature status:

- Package signature shows VALID  
- Unusual behavior: postinstall reads environment and makes network POST  
- Key usage timestamps show signing activity at unusual times  
- Postinstall file reads and network POST are the IOCs  

Lab helpers: `detection-tools/signature-validator.js` performs behavioral scan. Full Sigma / YARA sketches live in `DETECT.md`.

Containment script:

1. Revoke compromised signing key immediately.  
2. Review all packages signed with that key in the suspicious window.  
3. `npm uninstall secure-utils`, then `npm ci --ignore-scripts`.  
4. Check captured-data.json for exfil timestamps.  
5. Notify users to re-verify packages signed with the compromised key.

Control that breaks the loop: behavioral analysis beyond signature verification. Monitor key usage for unusual patterns. Postinstall network POST and file reads are the IOCs. Key compromise detection and rotation procedures.
